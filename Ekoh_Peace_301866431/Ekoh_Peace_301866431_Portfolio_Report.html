1. Executive Summary & Selected Enterprise Case Study

NovaMart Retail Logistics & Storefront is an omnichannel e-commerce retail enterprise serving urban and regional consumers across West Africa. The enterprise distributes consumer electronics, personal computing, home appliances, fashion, and FMCG provisions. The database architecture is engineered to satisfy intense concurrent demand during regional promotional campaigns ("Black Friday"), supporting shoppers, warehouse inventory controllers, logistics dispatch operators, and automated payment gateways.

Rather than forcing all business workloads into a single database engine, NovaMart implements a Polyglot Persistence Architecture: (1) MySQL 8.0 (InnoDB) for ACID-compliant orders, financial payments, and stock audit ledgers; (2) MongoDB (Document Store) for dynamic, polymorphic product specifications and embedded customer reviews; and (3) Redis (Key-Value) for ephemeral shopping carts (with 7-day TTL expiration) and sub-millisecond stock decrement caching.

2. Portfolio Activity 1: Database Design & Relational Modelling (7 Marks)

An 8-table relational schema was implemented in MySQL 8.0 InnoDB (customers, customer_addresses, categories, products, orders, order_items, payments, inventory_logs) with strict foreign keys (ON DELETE CASCADE / RESTRICT) and check constraints (stock_quantity >= 0, unit_price > 0).

Mathematical Normalisation Proof (1NF to 3NF/BCNF):

  • 1NF: All attribute values are atomic; repeating product collections were isolated into order_items and multi-valued delivery addresses into customer_addresses.
  • 2NF: In composite relation order_items(order_id, product_id), non-prime attributes (product descriptions and current catalog prices) depend strictly on product_id. These were decoupled into products, ensuring every non-prime attribute in order_items depends entirely on the full composite key.
  • 3NF / BCNF: Eliminated transitive dependencies: order_id → customer_id → customer_email and product_id → category_id → category_name. Isolating categories and customers into independent relations ensures that for every functional dependency $X \rightarrow Y$, $X$ is a superkey, completely eliminating update, insertion, and deletion anomalies.

5. Portfolio Activity 4: NoSQL & Advanced Data Models (7 Marks)

To overcome the relational Entity-Attribute-Value (EAV) dilemma, NovaMart's catalog was modeled as rich BSON/JSON documents in MongoDB (nosql_model.json).

  • Polymorphic Specifications: Products store divergent attributes seamlessly (Laptops: ram_gb, processor; Suits: virgin_wool, fit_type; Rice: grain_length_mm, aging) without schema alteration.
  • Embedded Reviews: Customer reviews and aggregated ratings are embedded directly inside product documents, allowing product pages to be retrieved in a single $O(1)$ read without table joins.
  • Atomic Operations & Aggregation: Verified $push review additions, $inc counter updates, and executed a 4-stage aggregation pipeline calculating category satisfaction (Electronics: 4.94★ across 6 reviews; Groceries: 4.90★ across 2 reviews; Fashion: 4.70★).
  • Redis Caching Tier: Key-value store managing active user shopping carts with auto-expiring 7-day TTLs (HSET cart:session:<id>) and in-memory stock counters for flash sales.

6. Portfolio Activity 5: Distributed & Cloud Database Architecture (6 Marks)

NovaMart's multi-region distributed cloud topology was specified and validated through a production Docker Compose cluster (docker-compose-distributed.yml):

  • GTID Semi-Synchronous Replication: A primary master node handles all write transactions, synchronizing via Global Transaction Identifiers (GTID) to dedicated read replicas with zero transaction loss ($RPO = 0$).
  • Entity-Based Horizontal Sharding: Partitioned horizontally by customer_id using consistent hashing: $\text{Shard} = \text{MurmurHash3}(\text{customer_id}) \pmod N$, guaranteeing 98% of queries run as fast single-shard operations.
  • High Availability & Failover: Multi-AZ deployment across three availability zones with automated health monitoring and Raft quorum consensus ($RTO < 30\text{ seconds}$).
  • CAP & PACELC Trade-Offs: Enforcing CP (Consistency + Partition Tolerance) on financial checkout transactions, and AP (Availability with Eventual Consistency) on catalog browsing and reviews.

7. Individual Technical Reflection

7.1 Architectural Design Choices & Trade-Offs

The defining architectural decision was embracing Polyglot Persistence. While early prototypes explored storing polymorphic specifications within MySQL 8.0 JSON columns, querying deeply nested attributes and calculating cross-attribute facets proved computationally expensive. MongoDB's native document model eliminated the relational EAV anti-pattern, permitting zero-downtime catalog expansions. Conversely, maintaining customer financial ledgers and stock reservations in MongoDB would have sacrificed strict multi-table relational ACID guarantees. Pairing MySQL for transactional ledgers with MongoDB for product browsing achieved the optimal balance of consistency, latency, and operational flexibility.

7.2 Practical Engineering Challenges & Solutions

  1. Timezone DST Discontinuity During Bulk Seeding: When inserting 9,000 randomized orders, MySQL threw ERROR 1292: Incorrect datetime value due to Daylight Saving Time (DST) spring-forward hour jumps. Enforcing explicit UTC session timestamps (SET time_zone = '+00:00';) resolved the issue deterministically.
  2. Eliminating Intermediate Filesorts in Analytical Queries: In Portfolio 2, initial profiling revealed that filtering by order_status still incurred an expensive in-memory sort on order_date DESC. By aligning with B-Tree composite index mechanics—placing equality attributes before sorting attributes—the new composite index idx_orders_status_date traversed leaf pages in pre-sorted order, slashing latency by 42.1%.
  3. Mitigating Concurrency Lock Contention: Pessimistic row locking (FOR UPDATE) proved highly effective in preventing overselling, but holding locks during slow external payment gateway calls risks thread exhaustion. In the simulation, Session 2 was blocked for 2.64s. In production, row locks must be restricted to minimal critical sections, augmented by Redis in-memory atomic decrement guards.
